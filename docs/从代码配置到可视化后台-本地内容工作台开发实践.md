# 从代码配置到可视化后台：我为 Astro 博客做了一个本地内容工作台

静态博客最吸引我的地方，是它足够直接：文章是 Markdown，配置是 TypeScript，所有内容都跟着 Git 走，没有数据库，也没有需要长期维护的服务端。

但当配置越来越多，这种“直接”也会带来另一种摩擦。

改一个站点标题，要打开配置文件；调整评论系统，要找到嵌套对象；加一条友链，要注意字段名和数组格式；写文章时，还要手动维护 Frontmatter。对于熟悉代码的人来说，这些工作并不困难，但它们会不断打断写作。

于是我给这个 Astro 博客做了一个本地内容工作台：运行一条命令，在浏览器里写文章、改站点设置，并编辑 `src/config` 中的完整配置。

更重要的是，它没有把博客改造成另一套系统。文章仍然是 Markdown，配置仍然是 TypeScript，部署产物仍然是静态页面。

## 一、我不想做一个传统 CMS

最直接的方案，是接入一个成熟 CMS，或者自己做数据库、登录系统和管理接口。但这会改变项目的边界：

- 内容从 Git 仓库转移到数据库；
- 本地预览和线上内容可能出现两套状态；
- 需要部署并维护后台服务；
- 需要处理账户、权限、备份和安全问题；
- 原本简单的静态博客开始依赖持续运行的基础设施。

这些成本与我的需求并不匹配。我只需要在自己的电脑上，用更舒服的方式编辑仓库里的文件。

所以这个工作台从一开始就确定了三个原则：

1. 只在本机运行；
2. 直接读写现有项目文件；
3. 不破坏 Markdown、TypeScript 和 Git 工作流。

最终的启动方式只有一条命令：

```powershell
pnpm admin
```

它会启动一个监听 `127.0.0.1` 的 Node.js 服务，然后通过浏览器打开管理页面。这个后台不会进入 Astro 的静态构建产物，也不会部署到线上。

## 二、真正困难的不是页面，而是如何修改配置

文章相对简单：读取 Markdown，解析 Frontmatter，修改后再写回文件。

配置要复杂得多。

这个项目的 `src/config` 中有站点、个人资料、导航、评论、统计、字体、背景、友链、相册、音乐播放器、看板娘等多个模块。它们不是单纯的 JSON 文件，而是带有类型、注释、枚举和常量引用的 TypeScript。

如果后台直接改写 TypeScript 源码，就需要解决一系列问题：

- 如何可靠解析不同写法的对象？
- 如何保留注释和原有格式？
- 如何处理变量引用与动态生成的配置？
- 如何保证写回后仍能通过 TypeScript 检查？

为了一份本地后台，引入完整的 TypeScript AST 修改器显得过重。

我最后选择了“默认配置 + JSON 覆盖层”。

## 三、保留 TypeScript，用覆盖层承接后台修改

原有配置继续作为默认值存在：

```ts
export const commentConfig = withAdminConfig("commentConfig", {
  type: "none",
  twikoo: {
    envId: "https://twikoo.vercel.app",
    lang: "zh-CN",
  },
});
```

后台修改则写入 `src/config/adminConfig.json`：

```json
{
  "overrides": {
    "commentConfig": {
      "type": "twikoo",
      "twikoo": {
        "envId": "https://example.com",
        "lang": "zh-CN"
      }
    }
  }
}
```

`withAdminConfig()` 在模块导出时完成合并：

```ts
function mergeConfig(defaults, override) {
  if (override === undefined) return defaults;
  if (Array.isArray(defaults)) {
    return Array.isArray(override) ? override : defaults;
  }
  if (!isObject(defaults) || !isObject(override)) return override;

  const merged = { ...defaults };
  for (const [key, value] of Object.entries(override)) {
    merged[key] = key in defaults
      ? mergeConfig(defaults[key], value)
      : value;
  }
  return merged;
}
```

这里的规则很明确：

- 对象递归合并；
- 数组整体替换；
- 基础值使用后台保存的值；
- 没有覆盖项时继续使用默认配置。

这样做的最大好处，是后台从此不需要重写 TypeScript。默认值、类型和注释全部保留，Astro 代码仍然从原来的配置模块导入数据。

## 四、如何让后台读取“真实配置”

有了覆盖层，还要解决一个问题：后台怎样知道所有配置当前到底是什么？

简单扫描源文件并不可靠，因为配置可能引用枚举、常量，甚至由函数动态组合。

我的做法是写一个很小的配置加载器：

```ts
import {
  siteConfig,
  profileConfig,
  commentConfig,
  analyticsConfig,
  // ...
} from "../src/config/index";

const modules = {
  siteConfig,
  profileConfig,
  commentConfig,
  analyticsConfig,
  // ...
};

process.stdout.write(JSON.stringify(modules));
```

本地服务通过项目已有的 `tsx` 执行这个加载器。加载器真正导入 TypeScript 配置，然后输出 JSON。

这意味着后台看到的不是“从源码猜出来的值”，而是博客实际导出的有效配置，包括已经应用的覆盖项。

当前工作台可以读取 30 个 TypeScript 配置模块，再加上单独读取的自定义页脚 HTML，一共提供 31 个配置入口。

## 五、用递归表单代替 30 套手写页面

如果每个配置模块都手写表单，开发和维护成本会迅速失控。很多配置虽然业务不同，但数据结构只有几种：字符串、数字、布尔值、对象和数组。

因此我实现了一个递归表单生成器：

```js
function renderValue(value, path, key) {
  if (Array.isArray(value)) return renderArray(value, path, key);
  if (value !== null && typeof value === "object") {
    return renderObject(value, path, key);
  }
  return renderPrimitive(value, path, key);
}
```

它会根据值类型选择控件：

- 字符串显示为输入框或多行文本框；
- 数字显示为数字输入框；
- 布尔值显示为开关；
- 对象显示为可折叠分组；
- 基础类型数组显示为每行一项的文本框；
- 对象数组显示为卡片列表，并支持新增、移除和排序。

每个控件都带有一条 JSON 路径：

```html
<input data-config-path='["themeColor","hue"]' />
```

输入发生变化后，前端根据路径修改当前模块的内存副本。点击保存时，再把整个模块提交给本地服务。

通用表单解决了大部分工作，但“完全自动”并不等于“好用”。我另外维护了三类小型元数据：

- 模块名称和分组，让左侧导航使用中文；
- 枚举选项，让主题模式、评论系统类型等字段使用下拉框；
- 空数组模板，让空的友链、打赏者列表也能添加第一项。

这是一种折中：核心依然通用，但把真正影响体验的部分显式描述出来。

## 六、“常用设置”为什么没有被删掉

有了“全部配置”，似乎可以删除原来的快捷设置页。但完整配置更适合偶尔调整高级功能，并不适合每次都在几十个字段中寻找站点标题或主题色。

所以工作台保留了两个层级：

- “常用设置”负责站点信息、个人资料、主题和页面开关；
- “全部配置”负责所有可序列化字段。

新的问题也随之出现：同一个 `siteConfig` 可能从两个入口被修改。

为避免两套数据互相覆盖，服务端增加了双向同步：保存常用设置时更新已有的 `siteConfig`、`profileConfig` 覆盖快照；保存完整模块时，再把相关字段同步回常用设置。

这个细节不显眼，却决定了两个入口能否长期共存。

## 七、文章编辑的重点是“不要破坏未知字段”

文章编辑器使用 `gray-matter` 读取 Markdown Frontmatter。后台管理标题、发布日期、摘要、标签、分类、草稿、置顶、密码等字段，但文章里可能还有用户自己添加的字段。

直接重新生成整个 Frontmatter 会丢掉这些未知字段。因此保存时采用的是局部更新：

1. 找到后台负责的字段范围；
2. 替换已存在的字段；
3. 追加缺失字段；
4. 保留未管理字段；
5. 保留 Markdown 正文。

例如原文章里存在：

```yaml
date: 2026-08-07T17:15:09+08:00
custom: keep-me
```

即使后台修改标题和标签，这两个字段依然会保留。

新文章则使用排他写入，遇到同名文件时返回冲突，而不是静默覆盖。

还有一个很实际的导入场景：从其他平台复制过来的往往是一整份 Markdown，正文框开头已经带有 Frontmatter。如果仍把输入当作纯正文，右侧表单会生成一份新元数据，而原 Frontmatter 会落入正文。

现在保存前会先检查正文开头：如果存在完整的 `--- ... ---`，就导入其中的标题、日期、标签、草稿等字段，以粘贴内容为准更新右侧表单，同时把 Frontmatter 从正文中移除。这样既能直接迁移完整 Markdown，也不会在最终文件中产生两份元数据。

正文编辑本身也做了两处调整：

- 输入区从普通 `textarea` 换成 CodeMirror 6，行号、括号匹配、搜索替换、列表续写和 Markdown/MDX 高亮都交给编辑器；键盘 `Ctrl+S` 仍然是保存；
- 桌面端把“撰写”和“预览”并排显示并各自滚动，窄屏才退回标签切换，这样在电脑上不必来回点标签确认排版。

删除文章同样遵循“不破坏底层文件”的原则：它不会调用 `unlink`，而是把文件 `rename` 到 `.admin-trash/posts/<时间戳>/` 下，并在确认框中显示标题与文件路径。`rename` 是原子操作，同盘移动既快，也让误删可以手动找回。

## 八、一个本地工具也需要边界

“只在本机运行”并不意味着可以完全忽略输入校验。

这个工作台做了以下限制：

- 只绑定 `127.0.0.1`；
- 只允许保存白名单中的配置模块；
- 请求体最大 2 MB；
- 限制配置嵌套深度、数组长度和字符串长度；
- 拒绝 `__proto__`、`constructor`、`prototype` 等危险字段；
- 文章路径必须留在 `src/content/posts/` 中；
- 新文件名会过滤 Windows 非法字符；
- 后台静态资源响应带 CSP 和 `nosniff`。

自定义页脚 HTML 是有意保留的高级入口。它会进入最终页面，因此界面明确提示只填写可信内容。

## 九、端口冲突也是实际使用体验的一部分

本地工具最常见的问题之一，是上次启动的进程没有关闭。再次运行时，Node.js 会抛出一大段 `EADDRINUSE` 堆栈。

与其每次让使用者手动查进程，工作台在默认端口被占用时会自动尝试后续端口：

```text
端口 4322 已被占用，已自动改用 4323。

Lunan 内容工作台已启动：
http://127.0.0.1:4323
```

这并不是什么复杂功能，但它能显著降低日常使用中的挫败感。对应行为也有自动化测试，避免以后修改启动逻辑时退化。

## 十、我最终得到的不是“第二套博客”

这个后台没有成为新的内容来源，它只是现有仓库的一层编辑界面：

```text
浏览器表单
   ↓
本地 Node.js API
   ↓
Markdown / JSON / HTML 文件
   ↓
原有 Astro 构建
   ↓
静态站点
```

文章仍然可以用任意文本编辑器打开；配置仍然可以直接在 TypeScript 中修改；所有变化仍然能通过 Git 查看和回滚。

这也是我认为它最合适的地方：它降低了操作门槛，却没有夺走底层文件的可控性。

## 十一、这套方案的局限

这不是一个通用 CMS，也不应该被包装成一个通用 CMS。

目前它有几个明确边界：

1. 完整模块保存的是当前模块快照，不是逐字段最小差异；
2. 数组会整体替换，不做智能合并；
3. 后台只做通用 JSON 校验，没有为 30 个模块分别实现运行时 Schema；
4. 函数、类实例和其他不可 JSON 序列化内容无法编辑；
5. Markdown 预览使用 Marked，与 Astro 的完整插件链可能有细节差异；
6. MDX 只做近似预览与近似高亮，组件不会真正渲染；
7. 回收站只负责移入，查看、恢复与清理仍需手动操作；
8. 没有登录系统，因此只能在本机使用；
9. 部分构建期配置需要重启开发服务器；
10. 静态配置不适合保存真正的服务端秘密。

这些限制不是隐藏的问题，而是保持实现简单所做的明确取舍。

## 十二、如果把它迁移到其他静态项目

这套实现最值得复用的并不是页面样式，而是四个分离的层次：

1. **真实配置加载器**：通过项目运行时导入配置，而不是猜测源码；
2. **持久化覆盖层**：保留代码默认值，把可视化修改放在独立数据文件；
3. **递归表单生成器**：用数据类型覆盖大多数编辑场景；
4. **文件安全边界**：限制可写模块、目录、体积和字段结构。

如果项目配置更严格，可以把通用 JSON 校验替换成 Zod 等运行时 Schema；如果需要多人协作，再引入认证、数据库和发布流程。但在个人静态博客里，本地文件已经是最自然的数据源。

## 结语

很多工具并不需要从“平台”开始设计。

对于一个本地优先的静态博客，最合适的后台可能不是数据库、账号系统和云服务，而是一个尊重现有文件结构的编辑层。

一条启动命令，一个本地页面，一组可以继续被 Git 管理的文件——这已经足够让写作和配置维护轻松很多，同时保留静态博客原本的简单与透明。
