第一次部署网站时，很容易被一串名词包围：域名、DNS、服务器、Pages、CDN、对象存储、Serverless、CI/CD……它们经常出现在同一个控制台里，却解决着完全不同的问题。

理解云服务最有效的方法，不是背产品名称，而是先弄清楚一次网站访问经过了哪些环节。

## 一次访问是怎样完成的

从开发者视角看，网站上线通常经历：

```text
源码 → 构建 → 部署 → 获得服务地址 → 配置 DNS → 绑定域名 → HTTPS
```

从用户视角看，一次访问大致是：

```text
输入 https://blog.example.com
        ↓
DNS 查询这个域名应该去哪里
        ↓
CDN、边缘平台或服务器接收请求
        ↓
应用返回 HTML、CSS、JavaScript、图片或 API 数据
```

这条链路可以拆成几个彼此独立的层次：

| 层次 | 解决的问题 | 常见形式 |
| --- | --- | --- |
| 域名 | 网站叫什么 | `example.com` |
| DNS | 这个名字指向哪里 | A、AAAA、CNAME 记录 |
| 托管 | 静态文件放在哪里 | Pages、静态托管 |
| 计算 | 后端代码在哪里执行 | 云服务器、Functions、Workers |
| 分发 | 如何让不同地区访问更快 | CDN、边缘节点 |
| 存储 | 图片和附件放在哪里 | 对象存储 |
| 数据 | 业务记录放在哪里 | MySQL、PostgreSQL、KV |
| 加密 | 如何保护传输过程 | HTTPS、TLS 证书 |

把这些职责分开后，选型会简单很多。

## 域名、注册商和 DNS 不是一回事

域名是方便人记忆的互联网名称，例如 `example.com`。注册商负责域名注册、续费和所有权管理；DNS 服务负责回答“这个域名应该指向哪里”。

域名在哪里买，不代表 DNS 和网站也必须使用同一家公司。完全可以采用这样的组合：

```text
域名注册：服务商 A
DNS 托管：服务商 B
前端部署：平台 C
后端计算：平台 D
```

### Nameserver 决定谁回答 DNS

NS（Nameserver）记录表示某个域名由哪组权威 DNS 服务器管理。当你把域名的 NS 切换到新的 DNS 服务商后，A、CNAME、MX、TXT 等记录通常也要在新的控制台维护。

同一个域名不应随意混用两组内容不一致的权威 DNS，否则不同用户可能得到不同解析结果。

### 最常见的 DNS 记录

| 类型 | 作用 | 示例 |
| --- | --- | --- |
| A | 域名指向 IPv4 地址 | `api.example.com → 192.0.2.10` |
| AAAA | 域名指向 IPv6 地址 | `api.example.com → 2001:db8::10` |
| CNAME | 一个域名指向另一个域名 | `blog.example.com → project.pages.dev` |
| MX | 指定接收邮件的服务器 | 企业邮箱 |
| TXT | 文本验证和安全策略 | 域名验证、SPF、DKIM、DMARC |
| NS | 指定权威 DNS | DNS 服务商提供的 NS |

DNS 控制台中的 `@` 通常代表根域名，也就是 `example.com` 本身；`blog`、`api` 则对应不同子域名。

## 服务器、静态托管与 Serverless

### 传统服务器

云服务器本质上是一台长期联网运行的计算机。你可以在上面安装 Linux、Nginx、Java、数据库和其他软件，控制能力很强，同时也要自己负责系统更新、防火墙、HTTPS、进程管理、备份和监控。

典型链路是：

```text
域名 → 服务器公网 IP → Nginx → 应用进程
```

如果应用需要长期运行的进程、特殊系统依赖或精细的网络控制，服务器通常更合适。

### 静态托管

Vue、React、Astro 等项目构建后，往往会得到一个包含 HTML、CSS、JavaScript 和图片的目录。这类产物不一定需要自己购买服务器，可以直接放到静态托管平台。

```text
Git 仓库 → 自动构建 → 静态托管 → CDN → 用户
```

个人主页、博客、文档站和产品介绍页，通常优先考虑这种方式。

### Serverless

Serverless 并不是没有服务器，而是开发者不需要维护具体服务器。你提交函数或应用代码，平台负责运行环境、扩缩容和基础设施。

它适合流量有波动、逻辑相对独立的 API，也适合个人项目减少运维成本。但它可能存在运行时限制、冷启动、厂商接口差异和按量计费等约束。

## CDN、边缘节点和源站

CDN 会把可缓存内容分发到靠近用户的节点。用户不必每次都跨越很远的网络访问源服务器，图片、脚本和页面可以从附近节点返回。

源站（Origin）是内容真正来源的服务器或服务。CDN 没有缓存某个资源时，会回源获取，再视规则决定是否缓存。

边缘计算则进一步允许代码在靠近用户的节点执行。CDN 主要解决内容分发，边缘函数解决的是就近运行逻辑，两者经常由同一平台提供，但不是同一个概念。

## DNS 解析和代理也不是一回事

只使用 DNS 时，DNS 服务告诉用户真实目标，后续请求通常直接访问目标服务。

开启代理后，请求先经过代理平台，再由平台访问源站。中间层因此能够提供缓存、HTTPS、Web 应用防火墙和流量规则等能力。

可以用一句话区分：

> DNS 负责告诉用户“去哪里”，代理负责让请求“先经过我”。

## 对象存储、数据库和 KV 怎么分

### 对象存储

对象存储适合图片、视频、PDF、压缩包、用户上传文件和备份。文件通常通过 URL、厂商 API 或 S3 兼容接口访问。

### 关系型数据库

用户、订单、文章和评论等结构化业务数据，通常进入 MySQL、PostgreSQL 或其他数据库。关系型数据库支持约束、关联查询和事务，不能简单用文件存储替代。

### KV 存储

KV 以键值形式保存数据，适合配置、缓存、会话和简单状态。它的访问模型很直接，但不擅长复杂关联查询，也不是关系型数据库的通用替代品。

## Build 和 Deploy 的区别

Build 是把源码转换成可运行或可分发的产物：

```text
src → build → dist
```

Deploy 是把产物交给实际运行环境：

```text
dist → deploy → production
```

CI/CD 则把安装依赖、检查、构建和部署自动串联起来。例如推送到主分支后，由平台自动构建并发布。

## 常见项目应该怎么选

| 项目 | 常见起点 |
| --- | --- |
| 博客、文档、落地页 | 静态托管 + CDN |
| 带少量表单或 API 的网站 | 静态托管 + Serverless Functions |
| 需要用户、订单和事务 | 前端托管 + 后端服务 + 关系型数据库 |
| 依赖长期进程或特殊环境 | 云服务器或容器平台 |
| 图片、视频和下载文件较多 | 对象存储 + CDN |

选型时先问三个问题：应用是否需要后端代码，数据是否需要事务和复杂查询，自己是否愿意长期维护服务器。回答完这三点，很多云产品已经可以排除。

## 最后记住这些关系

```text
域名：网站叫什么
注册商：域名在哪里买和续费
DNS：这个名字应该去哪里
托管：网站文件放在哪里
计算：后端代码在哪里运行
CDN：内容如何更快到达用户
源站：内容真正来自哪里
对象存储：文件放在哪里
数据库：结构化业务数据放在哪里
Build：把源码变成产物
Deploy：把产物发布到运行环境
```

云平台的产品名称会变，但这些职责相对稳定。先理解问题属于哪一层，再选择产品，比从某个厂商控制台反推架构可靠得多。
