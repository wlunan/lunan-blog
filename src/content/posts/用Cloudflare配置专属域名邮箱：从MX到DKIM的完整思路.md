拥有自己的域名后，可以把邮箱地址从平台账号变成 `name@example.com`。它适合对外联系、投递简历，也方便以后更换实际邮箱服务而保留地址。

配置域名邮箱的核心不是“把网站接到 Cloudflare”，而是按照邮件服务商提供的值，正确添加 DNS 记录。

> 邮件服务商的套餐、控制台入口和 DNS 值可能变化。本文解释配置思路，不提供一组可以永久照抄的固定记录；实际操作应以服务商后台当时生成的内容为准。

## 开始前需要什么

- 一个自己可以管理 DNS 的域名；
- 一个支持自定义域名的邮件服务；
- 域名已经接入 Cloudflare DNS；
- 能登录邮件服务商和 Cloudflare 的管理后台。

企业微信或腾讯企业邮箱可以作为邮件服务示例，但是否免费、账户数量、容量和发信限制，应在开通时查看最新官方说明。

## 域名邮箱依赖哪些 DNS 记录

| 记录 | 解决的问题 |
| --- | --- |
| MX | 别人发来的邮件应该交给哪台服务器 |
| TXT/CNAME 验证 | 证明你对域名有控制权 |
| SPF | 哪些服务器被允许代表该域名发信 |
| DKIM | 用数字签名证明邮件来自授权系统，且内容未被篡改 |
| DMARC | SPF 或 DKIM 验证失败时如何处理，并把报告发给谁 |

MX 负责“收得到”，SPF、DKIM 和 DMARC 主要帮助收件方判断“这封信是否可信”。只配置 MX，邮件可能可以收发，但抗伪造和送达表现并不完整。

## 第一步：在邮件服务商后台添加域名

进入邮件服务商的域名管理页面，添加 `example.com`。平台通常会生成：

- 一条或多条 MX 记录；
- 一条域名所有权验证记录；
- SPF 记录；
- 可选或后续生成的 DKIM、DMARC 配置。

不要从博客文章里复制别人域名的验证 CNAME。验证值通常与账户或域名绑定，必须使用自己后台生成的内容。

## 第二步：把记录添加到 Cloudflare

在 Cloudflare 控制台进入对应域名的 DNS 记录页面，逐条添加邮件服务商给出的记录。

### MX：决定收件服务器

MX 记录通常包含主机名、目标服务器和优先级。优先级数字越小，一般越优先尝试，但最终应完全照服务商给出的值填写。

如果域名以前使用过其他邮箱服务，要检查旧 MX 是否仍然存在。两套邮件服务同时争夺同一个域名的 MX，可能导致邮件投递到错误平台。

### 验证记录：证明域名属于你

服务商可能要求添加 TXT 或 CNAME。它只用于验证或服务发现时，应保持 **DNS only**，不要开启 Cloudflare 的 HTTP 代理。

### SPF：不要创建多条策略

SPF 通常以 `v=spf1` 开头。同一个域名不应简单叠加多条独立 SPF 记录。如果既使用企业邮箱，又通过其他平台发信，应依据服务商说明把允许的来源合并到同一条策略里。

错误的 SPF 可能让合法邮件也无法通过验证，因此不要在不理解含义时直接把 `~all` 改成 `-all`。

## 为什么邮件记录不能开橙色云代理

Cloudflare 的常规代理主要处理 HTTP/HTTPS 流量，并不会默认代理 SMTP。MX 和 TXT 本身始终是 DNS only；用于邮件或域名验证的 A、AAAA、CNAME 也通常应该设为 DNS only。

如果把邮件主机指向了一个被代理的网页记录，邮件服务器可能连到 Cloudflare 的地址，而不是实际邮件服务。这也是邮件配置中最常见的错误之一。

## 第三步：回到服务商后台完成验证

DNS 保存后，需要等待解析传播。几分钟内生效很常见，但缓存和 TTL 也可能让等待时间更长。

可以先检查公开解析结果：

```bash
nslookup -type=mx example.com
nslookup -type=txt example.com
```

确认返回值与服务商后台一致后，再点击“验证域名”。验证通过后，创建成员或邮箱账号，并进行真实收发测试。

## 不要停在“能收发”

### 配置 DKIM

邮件服务商使用私钥给外发邮件签名，收件方通过 DNS 中的公钥验证签名。DKIM 记录通常带有选择器，不同平台给出的主机名和内容不同。

### 配置 DMARC

DMARC 建立在 SPF 和 DKIM 之上。刚开始可以先采用监控策略，收集报告并确认所有合法发信来源都已配置，再逐步调整为隔离或拒绝。过早使用严格策略，可能误伤自己仍未纳入认证的发信系统。

## 常见问题排查

### 无法收到邮件

- MX 是否填写正确；
- 旧邮件服务的 MX 是否仍存在；
- 邮件服务后台是否已验证域名；
- Cloudflare Email Routing 是否正在占用该域名的 MX；
- 退信里是否给出了更具体的错误码。

### 能收但发信容易进垃圾箱

- SPF 是否覆盖了实际发信平台；
- DKIM 是否通过；
- DMARC 是否与当前发信来源匹配；
- 发件地址、显示名称和邮件内容是否异常；
- 域名是否刚开始使用，尚未建立信誉。

### 网站和邮箱能否同时使用

可以。网站的 A、AAAA 或 CNAME 与邮箱的 MX、TXT 各司其职。只要记录不冲突，一个域名可以同时承载网站和邮件。

## 最后的检查表

- [ ] 使用的是自己邮件服务后台生成的记录
- [ ] 已删除冲突的旧 MX
- [ ] 邮件与验证用途的记录保持 DNS only
- [ ] 域名只有一条有效 SPF 策略
- [ ] 已配置并验证 DKIM
- [ ] 已规划 DMARC，而不是直接复制严格策略
- [ ] 已完成外部邮箱到域名邮箱、域名邮箱到外部邮箱的双向测试
- [ ] 没有把账户验证值、后台截图或管理信息公开到文章中
