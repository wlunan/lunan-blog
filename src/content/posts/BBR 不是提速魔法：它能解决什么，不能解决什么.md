一台日本的 VPS，国内访问总觉得慢。搜到的第一个答案几乎都是「开 BBR」。

BBR 确实有用，但它被神化得太厉害了。搞清楚它作用于哪一段链路之后，就不会再指望它把 50ms 的 RTT 变成 20ms，也不会因为「开了 BBR 但没感觉」而怀疑自己配置错了。

## 先拆解「慢」

国内访问日本服务器，数据要跨越一段很长的链路。可能出问题的地方至少有四种：

- 网络往返时间（RTT）本身较长；
- 某些时段线路拥塞；
- 链路上发生丢包；
- 服务器与客户端之间的有效带宽被限制。

这四件事不是一回事。**BBR 只处理 TCP 发送端的拥塞控制与发送效率，解决不了全部问题。**

比如说，运营商给你限了 20 Mbps，那么无论换什么拥塞控制算法，都突破不了这个上限。

## 拥塞窗口是关键

TCP 传输里有个核心概念叫**拥塞窗口**（Congestion Window，`cwnd`）：在收到确认之前，发送端最多可以向网络里塞多少尚未被确认的数据。

窗口太小，带宽吃不饱；窗口太大，路由器开始排队，延迟上升甚至丢包。

传统算法 CUBIC 主要根据**拥塞事件**（尤其是丢包）来调整窗口，然后按立方函数增长。它的隐含假设是：丢包意味着网络满了。

BBR 换了思路，它持续估算两个量：

- `BtlBw`：瓶颈带宽，这条路径最多能跑多快；
- `RTprop`：最小往返时延，这条路最短要走多久。

用这两个量算出合理的发送速率和在途数据量，再通过 pacing（发送节奏控制）按合适的速度发出去。

两者的区别可以这样理解：

| | CUBIC | BBR |
| --- | --- | --- |
| 依据 | 拥塞反馈（丢包） | 带宽与时延的估计值 |
| 行为 | 丢包就降速，然后慢慢涨回来 | 估算道路容量，控制发送节奏 |
| 弱项 | 在高延迟、随机丢包的链路上容易误判 | 对浅缓冲区、多流竞争的场景不一定占优 |

举个具体例子：中日线路其实能承载较高的速率，但因为往返时延长，发送端没有维持足够的在途数据，链路就跑不满。BBR 会尝试找到更合适的速率和数据量，让长距离链路发挥得更充分。

反过来说，如果瓶颈是运营商限速，BBR 也无法突破。

## 哪些场景可能有改善

关键在于区分「谁在发数据」。

| 使用场景 | BBR 可能带来的改善 |
| --- | --- |
| 从服务器向客户端传大文件 | 比较明显，服务器是 TCP 发送端，BBR 直接起作用 |
| 浏览器访问服务器上的大页面、大接口响应 | 有一定帮助，普通小接口改善有限 |
| 从客户端上传大量数据到服务器 | 基本没有，发送端是客户端，服务器开 BBR 管不到 |
| 从第三方网盘直接下载 | 没有，这条链路的发送端是网盘服务器 |

还有一点容易混淆：BBR 不会降低物理往返时延。原本 RTT 是 50ms，开了 BBR 也不会变成 20ms。它可能通过减少不必要的排队改善实际传输表现，但改变不了两地之间的距离。

## 怎么开启

先看当前状态：

```bash
sysctl net.ipv4.tcp_congestion_control
sysctl net.ipv4.tcp_available_congestion_control
```

需要内核版本 ≥ 4.9。写入配置文件：

```bash
sudo tee /etc/sysctl.d/99-bbr.conf <<'EOF'
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
EOF

sudo sysctl --system
```

验证：

```bash
sysctl net.ipv4.tcp_congestion_control   # 应输出 bbr
lsmod | grep bbr                         # 应能看到 tcp_bbr
```

如果这里没有 `bbr`，说明内核没编译这个模块，需要先升级内核。

## 关于 fq 和 fq_codel

很多教程强调必须配 `fq`。严格来说，较新的内核在 TCP 层已经实现了 pacing，不再强依赖 `fq` 这个队列规则。已经用 `fq_codel` 的话可以先保留，不能仅凭队列规则的名字判断配置有问题。`fq` 在高负载服务器上仍可能有优势，但那属于调优范畴，不是开 BBR 的前置条件。

## 怎么判断有没有效果

不要靠「感觉快了」。固定测试条件：同一个测试文件、同一台客户端、同一时间段、同一个目标地址，对比三项指标：

- 实际吞吐量（大文件传输的平均速度）
- TTFB（首字节时间）
- 总耗时

如果只是访问一个几 KB 的接口，BBR 不会带来可感知的差异，这时候更值得优化的是连接复用、减少串行 API 调用、改善上游请求的并发策略。

## 别叠加一堆参数

服务器刚调完网络参数，最容易犯的错是把网上找到的 `sysctl` 全家桶一次性写进去：`tcp_fastopen`、`tcp_tw_reuse`、`tcp_max_syn_backlog`、各种 buffer 大小……出了问题根本无法定位是哪一个改坏的。

正确顺序是先只开 BBR，观察一段时间，确认瓶颈到底在哪，再决定要不要动下一项。而且大多数「跨境慢」的真实原因，往往不在内核参数表里，而在线路、源站响应速度和 CDN 策略上。

BBR 是让发送端更合理地利用已有的路，不是把路修短。想清楚这一点，很多优化决策会简单很多。
